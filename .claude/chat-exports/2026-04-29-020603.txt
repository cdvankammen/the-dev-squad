  # Topic-Aware Coding Skill
  
  You are enhancing a coding task with architectural context from topic
  documentation and managing documentation updates when needed.
  
  ## Token-Efficient Loading Strategy
  
  The system has three layers, loaded progressively:
  
  1. **TOPIC_REGISTRY.md** (ultra-lightweight inventory) - Load FIRST
  2. **topic/README.md** (concept overview) - Load when relevant
  3. **topic/USAGE|CONSTRAINTS|DESIGN.md** (details) - Load when needed
  
  **⚠️ Legacy Compatibility:** Prior topics may use `CONTRACTS.md` instead of
  `CONSTRAINTS.md`. These are equivalent—CONTRACTS is the legacy name. Always
  treat CONTRACTS.md as CONSTRAINTS.md when encountered.
  
  ## Invocation Modes
  
  ### Mode 1: Quick Inventory
  **When:** User says "load topics", "load context", or needs topic overview
  **Goal:** Fast catalog of available topics
  
  **Action:**
  1. Read ALL `**/docs/context/TOPIC_REGISTRY.md` files (workspace + submodules)
     - Ultra-lightweight: Just topic names, one-liner, key paths
     - Target: <100 tokens per topic, entire file <2k tokens
  2. Report topic counts by repository
  3. Exit (don't load full topic READMEs yet)
  
  **Result:** Complete inventory in minimal tokens
  
  ### Mode 2: Task-Specific Loading
  **When:** User has coding task, question, or technical request
  **Goal:** Load only relevant topics with progressive depth
  
  **Action:**
  1. Identify working repository (workspace vs submodule)
  2. Read that repository's `docs/context/TOPIC_REGISTRY.md`
  3. Match user's keywords/file paths to topics from registry
  4. Load relevant topic READMEs only
  5. Load USAGE/CONSTRAINTS/DESIGN if task requires detail
  6. Execute task
  
  **Result:** Targeted context, minimal token usage

  Be judicious about which topics to load. Apply these filters:

  ## Step 3: Load ONE Detail File (Usually USAGE.md)
  
  **STOP. Before loading any detail files, ask: "Is the user writing code or
  asking why?"**
  
  - **Writing code** (adding, modifying, implementing) → Load **USAGE.md only**
  - **Asking why** (rationale, trade-offs, debugging architecture) → Load
  **DESIGN.md only**
  - **Just exploring** (understanding concepts) → Load **README.md only** (no
  detail files)
  
  **Default to USAGE.md.** If the task involves writing or changing code,
  USAGE.md is almost always the right choice — even if the code involves error
  handling, retries, validation, or other things that sound like "constraints".
  USAGE.md contains the how-to patterns for all of these.
  
  **Do NOT load multiple detail files.** Pick ONE: USAGE.md, DESIGN.md, or
  README-only. Loading multiple detail files "to be thorough" defeats
  progressive loading.
  
  **Exception:** CONSTRAINTS.md is a validation checkpoint, not a detail file.
  You may skim it briefly (30 seconds before/after coding) as a guardrail check
  without it counting toward your "one detail file."
  
  **Common mistake:** Loading DESIGN.md for "how do I add code" questions.
  Adding code = USAGE.md. DESIGN.md is for understanding *why* existing code
  works the way it does.

  ### Staleness Awareness
  
  **Stability Indicators** in TOPIC_REGISTRY.md:
  - `[S]` Stable - core architecture, rarely changes
  - `[V]` Evolving - active development, regular changes
  - `[X]` Experimental - prototype, frequent churn
  
  **Staleness Thresholds** (based on `Last Validated` in topic README):
  
  | Stability | Trust Fully | Verify Against Code | Consider Stale |
  |-----------|-------------|---------------------|----------------|
  | Stable [S] | < 90 days | 90-180 days | > 180 days |
  | Evolving [V] | < 30 days | 30-60 days | > 60 days |
  | Experimental [X] | < 7 days | 7-14 days | > 14 days |
  
  **Git-Based Validation** (optional, for mismatch detection):
  
  When in a git repository, validate declared stability against actual churn:
  
  ```bash
  # Check if in git repo (skip validation if not)
  git rev-parse --git-dir 2>/dev/null || echo "Not a git repo - skip validation"
  
  # Count commits to topic's code paths in threshold period
  git log --oneline --since="90 days ago" -- src/auth/ | wc -l
  ```
  
  **Mismatch Warnings**:
  - Stable topic with high commit count → documentation may be outdated
  - Evolving topic with zero commits → may have stabilized, consider upgrading
  to [S]
  - If not in git repo, trust declared stability without validation

  CONSTRAINTS.md is categorically different from USAGE/DESIGN—it's a guardrail
  that doesn't count toward the "load ONE detail file" rule.
  
  **When to skim it (30 seconds max):**
  1. **Before writing code** — Quick scan for MUST/NEVER invariants to avoid
  violations
  2. **After writing code** — Verify new code doesn't break hard constraints
  
  **Key principle:** Brief skim only. Never use CONSTRAINTS.md as your primary
  source for "how to" guidance—that's what USAGE.md is for. CONSTRAINTS
  complements USAGE; it doesn't replace it.
